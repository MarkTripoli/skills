## Decomposition

**Shared boundary.** An opt-in scanner emits `{schema_version, finding_id, repository, revision, rule_id, path, line, severity, scanner, message, evidence_ref}`. `repository` is a canonical target identifier; `finding_id` is a deterministic identity for this scan's target revision, scanner, rule and location, never a plaintext secret. Disposition refers to that `finding_id`; an accepted-risk rule instead matches the stable `{repository, rule_id, anchored path pattern, expiry, reason}` so a later revision does not silently evade or inherit a scan-specific identifier. Require an exact path by default; an operator must explicitly choose broader glob scope. `evidence_ref` points at redacted diagnostics. Missing/failing scanner or invalid normalization is `incomplete`, never clean. SARIF may be an adapter, not a second core. This avoids the upstream finding/suppression field mismatch (`U:plugins/dev-team/knowledge/security-primitives-contract.md:114-127`; `U:plugins/security-assessment/scripts/apply-accepted-risks.sh:269-282`). The public contract is versioned in-repo, not an assumed npm publication: both packages are private (`P:package.json:1-13`; `A:package.json:1-13`).

**Publication boundary.** First map existing `describe-pr` draft-hosting, artifact-only commits, hosted capture/comment, code-review status, optional verification, app-test policy and Atomic proof rules (`P:skills/delivery/describe-pr/SKILL.md:43-82`; `P:atomic/lib/controller.mjs:112-133,171-191`). Then extract one host-neutral decision over `{repository, base_revision, head_revision, substantive_diff_digest, review_status, review_artifact_digest, verification_requirement, verification_status, verification_artifact_digest, capture_status, tested_code_revision, capture_url}` plus draft/final state. Only explicitly indexed task-artifact-only commits may advance HEAD without invalidating tested code; no arbitrary source or documentation change is exempt. A draft created solely to host a capture may proceed with `incomplete` proof but cannot become ready or publish the final body. Final publication requires clean current review, passing verification when required, acceptable current capture and hosted URL; the distinct comment/final-body check retains its existing order. Return `pass | incomplete | stale` with reasons. Public and Adyton readers translate their different artifacts to this decision; neither changes the other's storage. Skills invoke it even without agent hooks. An explicit bypass is recorded as `override`, never `pass`, and cannot relax any existing required publication rule. Tool interception is cooperative, not a hostile-user guarantee.

**Cost and scope boundary.** Ordinary delivery keeps its current security review and verification. Opt-in assessment invokes available scanners and one bounded contextual reviewer only for actionable findings. A deterministic seeded-security grader measures expected detections, missed defects, extra emissions, redaction, suppression expiry, uncertain reachability and report fields; a separate opt-in live matched delivery-versus-solo fixture measures acceptance, elapsed time and spend. Record model/provider, tool versions, repo/fixture revisions, wall time, price basis and raw output. Unknown cost stays unknown; a completed grader without matched live observations does not satisfy the parallelism promotion gate. Require no lower acceptance or defect recall and no more than 20% additional measured spend on the tested fixture before enabling opt-in parallelism; otherwise leave it disabled and report the result. This threshold is a *proposal for the review gate*, not an empirical claim or automatic default change. Historic upstream figures cannot predict either repo's outcome.

**What not to copy.** No unconditional five-agent security swarm, mandatory per-edit SAST, commit-attempt review gate, automatic auto-merge, generic second controller beside Atomic/First Sergent, unbounded child parallelism, private-secret aggregation by default, or red-team requests against external endpoints. Source-pattern service graphs remain hypotheses, not proof of runtime traffic. No claim of vendor-independent hooks where a runtime lacks an event interface.
