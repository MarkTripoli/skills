## Summary

The three systems overlap on staged research, plans, independent review and verification. The upstream four-command workflow is primarily a Claude Code skill/agent instruction chain; its Python script is a narrower independent dispatcher rather than an executable implementation of all four commands. Public skills use canonical independent skill phases and optional Atomic/First Sergent control; Adyton shares the phase intent but differs in task storage, GitLab publication, and a Jira-led paired-repository path. Security-assessment adds a distinct multi-target scanner/judgment/report pipeline beyond either local collection's security review axis. None of these facts implies the upstream plugin succeeds more often in production.

## Detailed Findings

### 1. The upstream development path is a skill chain plus a distinct script dispatcher

`/specs` authors Intent, Architecture and Acceptance Criteria and runs a consistency gate; `/plan` creates vertical slices, Gherkin scenarios and a dependency graph, dispatches tier-selected critics and presents a human gate; `/build` implements a slice in one-agent small batches, gathers fresh test and runtime evidence, runs scoped review checkpoints and an end review; `/pr` runs final checks and creates a GitHub PR (`U:plugins/dev-team/skills/specs/SKILL.md:78-155,207-231`; `U:plugins/dev-team/skills/plan/SKILL.md:53-101,130-162`; `U:plugins/dev-team/skills/build/SKILL.md:21-31,107-173,277-330`; `U:plugins/dev-team/skills/pr/SKILL.md:29-149,176-278`). The plan critic requires a real Agent/Task dispatch tool, rather than treating a self-review as independent (`U:plugins/dev-team/skills/plan/SKILL.md:20-29,132-151`). `/build` defaults to one worker, and concurrent worktrees require an explicit jobs setting and reconciliation barrier (`U:plugins/dev-team/skills/build/SKILL.md:139-155`).

A separate `scripts/orchestrator.py` runs `claude -p --agent` personas for research, plan and implementation and saves phase JSON. Its trivial classification returns success without implementing; the standard/complex implementation roster is a fixed synthetic slice. Failed research/plan persona results are recorded rather than preventing the next phase (`U:plugins/dev-team/scripts/orchestrator.py:306-341,362-417,735-812`). The script and slash-skill chain therefore have different completeness contracts. Specs usually persist under `docs/specs/`, plans under `plans/`, and runtime hook state under project `.claude/`; the script's phase state is invocation-CWD-relative (`U:plugins/dev-team/skills/specs/references/persistence.md:7-29`; `U:plugins/dev-team/skills/plan/SKILL.md:33-38`; `U:plugins/dev-team/hooks/lib/artifact_paths.py:25-61`; `U:plugins/dev-team/scripts/orchestrator.py:832-876`).

#### Testing patterns

`U:tests/scripts/test_orchestrator.py:537-595,1472-1617,2115-2255` exercises persona dispatch, critics and phase state with mocked subprocesses. `U:plugins/dev-team/tests/hooks/test_pre_pr_review.py:1-162` uses hermetic Git repositories. These do not execute the entire four-command feature workflow against a live application.

### 2. The upstream security path joins tool detections, judgments and cross-repository heuristics

The declared pipeline runs recon, SARIF-first static tools (Semgrep, Gitleaks, Trivy, Hadolint, Actionlint), five judgment agents, accepted-risk suppression, false-positive disposition and severity floors, then narratives/compliance and a report. Independent target stages run in parallel, while the cross-repo service/credential stage can start after recon; the final report joins them (`U:plugins/security-assessment/skills/security-assessment-pipeline/SKILL.md:19-75,79-153`). The versioned dev-team contract defines RECON, unified finding and disposition envelopes; source tools normalize into those contracts (`U:plugins/dev-team/knowledge/security-primitives-contract.md:17-25,108-145`). The executable accepted-risks script requires a JSON entry with rule ID, path glob, reason and expiry, logs expired/suppressed records, and atomically replaces the finding stream (`U:plugins/security-assessment/scripts/apply-accepted-risks.sh:103-145,245-327`).

Cross-repo service edges are source-pattern/package/Kubernetes heuristics rather than observed runtime calls (`U:plugins/security-assessment/harness/tools/service-comm-parser.py:20-44,70-120`). Shared credential matching hashes `.env*` values and writes SARIF; its condition is two locations, not two distinct repositories, so the output can include two locations in one repository (`U:plugins/security-assessment/harness/tools/shared-cred-hash-match.py:28-67,71-100`). The separate red-team Python harness performs config/scope checks, sequential probes, and an audit trail; the safety claim is self-owned/private targets by default, with an explicit authorization artifact for public targets (`U:plugins/security-assessment/harness/redteam/config.py:82-132`; `U:plugins/security-assessment/harness/redteam/orchestrator.py:132-205`). Report verification logs failure without blocking publication (`U:plugins/security-assessment/skills/security-assessment-pipeline/SKILL.md:138-153`).

The unified finding contract locates optional source pointer at `metadata.source_ref` and requires `file`; the suppression script reads a top-level `source_ref`. No bridging conversion was confirmed in this pass, so suppression compatibility with a bare canonical finding remains an open factual question (`U:plugins/dev-team/knowledge/security-primitives-contract.md:114-127`; `U:plugins/security-assessment/scripts/apply-accepted-risks.sh:269-282`).

#### Testing patterns

`U:tests/security-assessment/scripts/apply-accepted-risks.test.sh:105-205` tests exact/glob/expiry cases, and `U:tests/security-assessment/harness/scope_enforcement_test.py:96-160` tests red-team config refusal. The synthetic comparative fixture tests finding recall and suppression, not runtime attack chains (`U:evals/comparative/README.md:1-26,45-56`).

### 3. Public skills already run a portable, artifact-backed delivery chain

The public collection's canonical phase skills run independently in Claude Code, Codex, OMP and Pi; runtime builds adapt invocation, while Atomic requires explicit installation (`P:shared/CONVENTIONS.md:3-11`; `P:scripts/lib/build.mjs:10-19,98-144`). `lean`, `full`, `prd`, `bugfix`, `epic`, and `program` chains route from research through implementation/reproduction to independent verification, code review, behavior capture and PR description (`P:workflows/delivery.md:75-99`; `P:atomic/lib/controller.mjs:13-35,57-133`). An indexed, committed, immutable task ledger binds iterations to hashes and current pointers (`P:shared/CONVENTIONS.md:14-47,74-105`; `P:shared/task-artifacts.mjs:49-88`).

Atomic dispatches each skill with `context: 'fresh'`, checks that the expected new artifact exists, records model attempts and invalidates proof on code revision changes; approval is bound to artifact hash in native UI (`P:atomic/lib/controller.mjs:204-265`). Fixed workflows select their next eligible step deterministically; adaptive paths use JEV among eligible choices (`P:atomic/workflows/delivery.ts:128-151`). Epic children are separate worktrees, but the native parent child-wave loop starts them serially and waits for merge evidence (`P:atomic/workflows/delivery.ts:156-173`). First Sergent is a separate optional fresh-worker chat liaison, not a mandatory second layer (`P:skills/delivery/agent-first-sergent/SKILL.md:8-25,49-81`).

The code-review phase checks correctness, readability, architecture, security and performance, with critical/major findings requiring repair (`P:skills/delivery/review-code/SKILL.md:28-50`). The independent verifier reruns acceptance/repository checks, and the controller always requires a current code review, behavior capture and hosted PR evidence even if `verify=false` (`P:skills/delivery/verify-implementation/SKILL.md:8-56`; `P:atomic/lib/controller.mjs:112-133,171-191`). The security review axis is not a tool-first, multi-target SAST/FP/compliance pipeline in this chain (`P:atomic/lib/controller.mjs:13-35,112-133`).

#### Testing patterns

`P:tests/atomic-controller.test.mjs:47-125,312-402` exercises phase ordering, stale capture rejection and publication prerequisites; `P:tests/route-model.test.mjs:46-105` tests model routing; `P:evals/run.mjs:1-18,84-119` can run live OMP skill sessions against isolated fixtures, separately from `npm test`.

### 4. Adyton shares the lifecycle but adds company-specific cross-repository coordination

Adyton's Atomic workflow has the same preparation/gate pattern and fresh child sessions, with GitLab MR-specific phases and `gates=mr` rather than `gates=pr` (`A:atomic/workflows/delivery.ts:10-35,91-179`). Its task convention is intentionally different: ignored local numbered artifacts revised in place, rather than public committed indexed immutable series (`A:shared/CONVENTIONS.md:13-21,59-71`; `P:shared/CONVENTIONS.md:36-47,74-105`). Copying a public task artifact directly into Adyton's controller therefore does not preserve the same storage contract.

`video-iterative-orchestration` gives each Jira Story an implementation owner; a cross-layer story gives one agent paired backend/frontend worktrees, and a dependent worktree starts from a verified submitted parent commit. Its ledger tracks parent SHA, states, evidence, MRs and pipeline gates; local verification is not the submitted/merge-ready state (`A:skills/delivery/video-iterative-orchestration/SKILL.md:24-33,50-80,82-105,137-152`). Jira breakdown and Story QA are separately owned (`A:skills/jira-issue-hierarchy/SKILL.md:8-18`). A Slack control plane supplies optional status and owner steering; its absence is non-blocking unless explicitly made a gate (`A:skills/delivery/agent-slack-control-plane/SKILL.md:20-50,175-188`). These are instruction contracts; no real cross-repository run was witnessed.

Both collections' Safety Dance is a separately installed local Git gate/daemon that admits pushes and runs configured review/validation before publication, with an explicit trusted-same-user threat model (`P:docs/safety-dance.md:3-26`; `A:docs/safety-dance.md:5-31`). Adyton CI runs tests and release-specific vulnerability checks; neither repository's standard delivery chain invokes the upstream security-assessment pipeline (`A:.gitlab-ci.yml:1-70`; `A:atomic/workflows/delivery.ts:91-179`).

#### Testing patterns

`A:evals/run.mjs:1-18,83-103` runs live OMP scenario sessions against fixture repositories; `A:tests/evals.test.mjs:1-118` tests grader boundaries. `A:tools/safety-dance/internal/daemon/hook_e2e_test.go:16-30,87-113` tests the Git admission hook. No live Jira/Slack/paired-worktree scenario was run in this research.

### 5. Hooks differ by enforcement edge, not by a binary present/absent distinction

Upstream dev-team registers Claude Code SessionStart, PreToolUse, PostToolUse, Stop and SubagentStop handlers, including PR review, edit guards, telemetry, dispatch records and context checks (`U:plugins/dev-team/hooks/hooks.json:3-175,177-312`). The current PR review gate binds a branch diff hash to recent registered-agent dispatch evidence; it blocks `gh pr create` on normal missing/invalid evidence, allows an explicit audited bypass and fails open on an unexpected top-level exception (`U:plugins/dev-team/hooks/pre_pr_review.py:30-65,603-694`). Commit review in the main README is stale relative to this implementation (`U:plugins/dev-team/tests/hooks/test_pre_commit_review.py:1-13,48-59`). The security plugin's PostToolUse scanner is advisory, silently skips missing tools and exits 0; its Gitleaks branch parses a report only after a zero-status detection command (`U:plugins/security-assessment/hooks/static-scan-on-edit.sh:12-22,54-69,101-115,119-152`).

Our public and Adyton collections already have a Conventional Commit `commit-msg` hook and optional Safety Dance managed pre-receive hook. Their scope is Git messages/push admission, not a portable agent-tool event boundary (`P:.githooks/commit-msg:1-4`; `A:.githooks/commit-msg:1-4`; `P:tools/safety-dance/internal/git/hook.go:18-34,37-125`). Hook registration alone does not show which hooks are active in a user's environment. Upstream's earlier 45-run benchmark recorded a plugin hook loading deviation on Claude Code 2.1.214, so installation behavior needs independent runtime verification (`U:reports/orchestration-benchmark-2026-07-18.md:146-159`).

#### Testing patterns

`U:plugins/dev-team/tests/hooks/test_pre_pr_review.py:1-162` tests review hash/ledger cases. `P:tools/safety-dance/internal/pipeline/steps/pr_security_test.go:9-46` checks evidence confinement. `A:tools/safety-dance/internal/daemon/hook_e2e_test.go:87-113` exercises Git hook admission. No cross-harness agent-event-hook suite was located in the local delivery sources inspected.

### 6. Evaluations separate deterministic grading from optional expensive dispatch

Upstream CI validates the structural fixture corpus on relevant PRs; live `claude -p` dispatch is opt-in via `run-eval` or manual force and requires API credentials (`U:evals/README.md:8-41`). Its historical baseline records measured provenance and three trials, not a current-run model identity (`U:evals/baseline.json:1-8`). The code-review benchmark uses known-defect commits and location-tolerant grading, but its own README says the live full dataset sweep has not run (`U:evals/code-review-benchmark/README.md:1-25`; `U:evals/code-review-benchmark/scorer.py:1-37`). The April 21 synthetic security scorecard reports 18/26 reference and 21/26 tool-heavy recall, 2/2 suppression for both, and 28 versus 54 extra emissions; these archived values do not establish current checkout performance (`U:evals/comparative/reference-baseline/2026-04-21/scorecard-after-fixes.txt:5-10`; `U:evals/comparative/README.md:1-26`).

Upstream's earlier 45-run orchestration benchmark reports solo versus orchestration medians of $0.172 versus $0.646 on trivial, $0.265 versus $0.749 on standard, and $0.752 versus $2.259 on complex fixtures; solo passed 15/15, orchestration 14/15 (`U:reports/orchestration-benchmark-2026-07-18.md:1-6,34-76`). It explicitly limits generalization to its three fixtures (`:105-125`). Public and Adyton `evals/run.mjs` execute actual OMP skill phases against isolated fixtures and grade artifact/handoff/commit behavior; neither inspected runner proves defect-detection recall or end-to-end project success (`P:evals/run.mjs:1-18,84-119`; `A:evals/run.mjs:1-18,83-120`).

## Architecture Documentation

The upstream system has two orchestration surfaces: Claude Code slash-skill/agent contracts and a separate Python persona runner. Its security plugin consumes a versioned dev-team data contract and uses scripts for detector normalization, suppression and report checks. Public skills instead separate portable skill text from optional Atomic/First Sergent control with indexed task state. Adyton adapts analogous phases to GitLab and Jira while retaining a different task artifact contract. The security pipeline has scanner outputs joined by a finding schema, whereas the local review loop has a security axis without a separate scanner-to-finding-to-disposition interface.
