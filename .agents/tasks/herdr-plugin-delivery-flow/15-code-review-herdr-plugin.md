## Critical and Required Findings

Gate: critical- or major-severity findings only.

### CR-005 The blocked-startup wait has no `--until`, so it returns at once on `blocked` and the command is typed into an approval dialog

- type: Potential issue
- severity: major
- category: Functional correctness
- location: `skills/delivery/herd-next/references/stop_hook.sh:138`, and the same command in prose at `skills/delivery/herd-next/SKILL.md:68`
- failure mode: `herdr agent start` returns `agent_not_ready` only when the new agent is blocked during startup, which is the common shape of a runtime's first-run trust or permission dialog in a pane opened at a fresh worktree. The recovery is `herdr agent wait "$name" --timeout 30000` with no `--until`. Herdr's contract for a bare `agent wait` is to settle on `idle`, `done`, or `blocked`, so it matches the agent's current state immediately and exits 0. The script then runs `pane rename` and `pane send-text "$pane" "$cmd"`, writing the handoff command as raw characters into whatever UI holds the pane, and reaches `done=1` so the teardown trap does not fire. The user is left with a pane labelled as ready whose agent never received the command, and whose approval dialog has just been typed into; a dialog that selects on a keypress can be answered by those characters. `SKILL.md:68` states the opposite intent in the same breath as the broken command: "report a still-blocked agent in the reply rather than sending input to it". The skill body cannot deliver that, because the wait it prescribes cannot distinguish a blocked agent from a ready one.
- evidence or reproduction: `herdr agent wait --help` on this machine: "Without `--until`, matches idle, done, or blocked." `herdr --skill` line 143: "Without `--until`, standalone `agent wait` uses the same settled-state defaults as `agent prompt --wait`", and line 133 defines those defaults as "the first settled `idle`, `done`, or `blocked` state". Line 125 states the requirement the change misses: "If the agent is blocked during startup, the command returns `agent_not_ready` immediately but keeps the name available for `agent read` and `agent send-keys`. Wait until the agent becomes idle before prompting it." Line 59 defines `blocked` as "Herdr recognized an approval or question UI", and line 159 adds "If a wait fails or returns `blocked`, inspect `agent get` and `agent read` before deciding what input to send." Reproduced against the shipped script with a mock `herdr` whose `agent start` emits `{"error":{"code":"agent_not_ready","message":"blocked"}}` on stderr with exit 1 and whose `agent wait` returns `{"result":{"agent":{"status":"blocked"}}}` with exit 0: the call log is `agent start ...`, `agent wait herdr-plugin-del-fix-code-review --timeout 30000`, `pane rename ...`, `pane send-text pNEW /fix-code-review @14-code-review-fixes-herdr-plugin.md`, and the script exits 0 with nothing cleaned up. The emitted wait carries no `--until`, which is the whole finding. Note this is not CR-004 returning: CR-004 was the branch being unreachable and it is fixed, which is what makes this branch's own semantics observable for the first time.
- fix direction: pass the target state explicitly, `herdr agent wait "$name" --until idle --until done --timeout 30000` (`--until` is documented as repeatable, and `herdr --skill` line 59 gives `idle` and `done` as the two states that mean ready for input). In `stop_hook.sh` keep the existing `|| exit 0`, which then means a real timeout and lets the trap remove the pane. In `SKILL.md:68` state the same flags so the by-hand mode and the hook still agree, and keep the sentence about reporting a still-blocked agent, which becomes true once the wait can fail on that state. Because the same prescription is in `04-plan-herdr-plugin.md:133`, correct it there too or the next reader reintroduces it.

- type: Potential issue
- severity: minor
- category: Functional correctness
- location: `skills/delivery/herd-next/SKILL.md:58`
- evidence: `herdr` rejects a bad name with `invalid_agent_name`: "agent name must start with a lowercase letter and contain only lowercase letters, digits, '-' or '_' (1-32 characters)", and `herdr --skill` line 57 gives the pattern as `[a-z][a-z0-9_-]{0,31}`. `04-plan-herdr-plugin.md:31` recorded it: "Agent names must match `[a-z][a-z0-9_-]{0,31}`". `stop_hook.sh:128` enforces it, `case "$name" in [a-z]*) ;; *) exit 0 ;; esac`, and its comment at `:115` states the pattern. - suggestion: add the first-character rule to step 6, with what to do when the slug cannot supply one, so the skill body and `stop_hook.sh:128` agree again.

### ADV-014 The signal traps tear down and then let the script keep running

- type: Refactor suggestion
- severity: trivial
- category: Stability and availability
- location: `skills/delivery/herd-next/references/stop_hook.sh:26-34`
- evidence: `trap cleanup EXIT INT TERM HUP` was round 14's fix for ADV-006 and it does close the pane on a signal, but `cleanup()` does not exit and does not set `done=1`. A bash signal handler that returns resumes the interrupted script, so after `SIGTERM` the run continues against a pane that no longer exists, fails at the next `herdr` call, exits 0, and runs `cleanup` a second time from the `EXIT` trap. The outcome is the wanted one and the second close is a no-op, so nothing breaks; it is just more code running after the decision to stop.
- suggestion: either set `done=1` as the last line of `cleanup`, or split the traps, `trap cleanup EXIT` and `trap 'cleanup; exit 0' INT TERM HUP`, so a signal ends the script where it is caught.
