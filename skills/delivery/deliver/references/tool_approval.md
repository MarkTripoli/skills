# Tool approvals

When this file applies, inspect the **current harness session** for an authoritative active tool-approval mode supplied by the host or already visible in session context. Do this before routing or creating a task. Classify it as `no-prompt`, `prompts possible`, or `unknown`; do not claim success from a config file, environment variable, installed CLI's `--help`, a newly spawned CLI, or one successful tool call. Those do not establish the current session's effective mode. Never change permission settings or bypass a prompt on the user's behalf.

| Harness | Sufficient active-session evidence | Guidance when prompts are possible or status is unknown |
|---|---|---|
| Claude Code | Host-reported `bypassPermissions` or `auto` mode. `acceptEdits`, `dontAsk`, `plan`, and Manual are not equivalent. | Check the live mode in the CLI footer or `/permissions`. To start a session in a no-prompt mode, see Claude Code's own documentation; do so only in a trusted isolated environment. |
| Codex | Host-reported `Full Access` (sandbox disabled **and** approval policy `never`), or a host-reported automatic approval reviewer; the latter may still restrict sandbox access. | Inspect `/status` in the running Codex UI. To start a session with full access, see Codex's own documentation; do so only in an externally isolated environment. Approval policy `never` alone can leave the sandbox restricted. |
| Oh My Pi | Host-reported active `tools.approvalMode: yolo` with no relevant explicit `prompt` policies; in ACP, `yolo` must be explicitly configured. `write` still prompts for execution. | Check **Interaction → Approvals** in `/settings`, including per-tool policies. For a new session, see Oh My Pi's own documentation. A separate `omp config get` is not proof of this session's overrides. |
| Pi | Core Pi has no per-tool approval mode; core tool calls do not request per-call approval. An installed permission extension can still prompt or deny. | If an extension is active or its behavior is unknown, inspect its own status and configuration and use its documented no-prompt option. |
| Portable session | No harness-level tool mode can be inferred from the skill install or `gates`. | Name the actual host and use its guidance above; if the host does not expose live status, say it cannot be verified. |

Emit a harness-specific **Tool approval preflight**: report the observed mode and `no-prompt` only with sufficient evidence; otherwise warn that prompts may occur or the active mode is unverified, and give the check step and point to the harness documentation for no-prompt mode. Carry the same result into the final answer. Continue delivery; the preflight is advice, not a new approval gate. Recommend unrestricted modes only in trusted, externally isolated environments. Even full access can retain organization safety restrictions. This check concerns *harness tool calls*, not task scope or human review: never change `gates` or suppress a manual phase handoff.
