# Repair the deciding failure

Use the affected PR's branch and actual source. Original task/context is useful when available; its absence alone does not prevent an authorized repair. Missing product source, essential credentials or a required before-edit baseline is a concrete blocker. Preserve unrelated work and explicit requirements.

## Ordinary CI and review work

Prioritize current-head CI on the ready frontier, then actionable review, then descendants. Read the failed job log, reproduce the deciding check, make the smallest appropriate fix and exercise the changed path. Choose regression coverage and review depth from the change's risk; a routine repair does not require a separate delivery artifact chain.

For review, verify the request against code and handle edited notes as new work. Reply with the deciding result and revision. Resolve handled resolvable items; retain disposition for non-resolvable notes. Refer disputed or scope-changing requests to the owner without stopping independent work.

Commit explicit source paths and push only within authority. Refresh the actual host head and required CI; an old green pipeline or a successful push is not current CI. Invalidate affected checks and any required source-bound receipts after a source change. Cancel unsafe queued enrollment before editing.

## Helpers and delegation are conditional

The repository installer supplies existing review/evidence companions; their availability does not make every companion mandatory. Use a relevant installed workflow when it fits the task, or investigate and repair inline. Missing optional helpers is not an observe-only restriction. Preflight an executable only when the operation actually needs it; do not substitute prose for specifically required executable proof.

For delegated work, provide the full PR identity, current head, authorized source paths/actions, deciding job or note version, applicable requirements and expected result. Keep one writer per source branch. Workers return changes/checks/pushed SHA and blockers; the orchestrator owns merges and external coordination. Reconcile a moved head before applying a result. When coordinator ownership applies, use its existing action-time gate; execute inline if that cannot be enforced for a worker.

## When delivery proof is explicitly required

Read the owner's request, repository rules and original task's evidence policy to determine required gates. Missing evidence blocks the operation requiring it, not diagnostics or unrelated work. Honor requirements that apply before editing. Existing new-only omission policies remain valid; reconstructing a baseline from post-fix behavior does not.

Run the installed delivery status helper when that contract is required:

```sh
node <skills-dir>/deliver/contract.mjs status <original-task-dir>
```

Use only the phases the applicable requirement needs: `verify-implementation`/`test-app` for requested verification, fresh `review-code` for required independent review, `record-evidence`/`iterate-evidence` for recorded proof, and `describe-pr` for required publication. An explicitly applicable full delivery contract retains its complete chain. Recordings use authentic current bytes, the original baseline policy and required source-bound seal/inspection; publication preserves the description and distinct evidence-comment links. Keep required receipts current after repairs and read back hosted results. Do not invent an inaccessible original task, baseline, seal or success.

Record required gate results with the tested SHA/fingerprint and actual receipt/readback. Before merging, verify required bindings plus current host checks/review/authority. Green CI does not replace explicitly required proof; absent optional proof does not add a new merge gate.
