# Stack merge procedure

Use this procedure separately for each PR in the recorded chain. A child targeting its parent's source branch is not ready for the final target until the parent is host-confirmed merged there. GitHub is the default; retain GitLab commands only for an explicitly selected GitLab repository.

1. Fetch source and target, and read current host state. On GitHub use `gh pr view <number> --repo <host/owner/repo> --json url,state,headRefOid,headRefName,baseRefName,mergeCommit,mergeStateStatus,reviewDecision,statusCheckRollup` and the installed `resolve-pr-reviews` GitHub protocol for paginated discussion reads. Record already-merged or genuinely missing PRs as skips. Require the same source SHA as the reviewed selection, the configured merge method, and current required checks. Use a clean isolated worktree; never displace owner work.
2. Merge the parent first and read its actual target commit. Find the child's actual fork point with `git merge-base`, inspect its child-only diff, and preserve that net change onto the refreshed target. Use `git rebase --onto <new-target> <child-fork-point> <child-source>` only when those commits represent the reviewed child delta. Retarget on GitHub with `gh pr edit <number> --repo <host/owner/repo> --base <target>` when needed. Compare the resulting diff and tree after a squash; do not blindly replay, skip, or reset the chain.
3. Push only the intended source branch with `--force-with-lease=<remote-ref>:<observed-old-sha>` when history changed. Re-read the host head and record the successful push time as this PR's review cutoff. Target changes, rewritten commits, and comment fixes can invalidate checks. Handle discussions through `resolve-pr-reviews`; resolve only handled items, retain their IDs, and report refused resolutions without bypassing host requirements.
4. Wait for current required checks on GitHub with `gh pr checks <number> --repo <host/owner/repo> --required --watch`, then refetch the head and check rollup. Missing or inaccessible required proof blocks the merge. For GitLab, require current revision pipelines and external checks through its existing protocol; synthetic merged-result pipeline SHAs require authenticated association with the selected source revision. Diagnose failures before retrying; older green checks do not pass.
5. Inspect new chain-related notes after each run-owned rebase, while checks run, and immediately before merging. Supply actionable notes to `resolve-pr-reviews`, then repeat affected push/check steps. Refresh source SHA, target SHA, reviews, required checks, and merge readiness before mutation. Respect host approval requirements without self-approval or protection bypass.
6. On GitHub merge with `gh pr merge <number> --repo <host/owner/repo> --match-head-commit <source-sha>` and the repository's configured `--squash`, `--merge`, or `--rebase` method. Do not use `--admin`. If a required queue accepts enrollment, record queued and read back `state` and `mergeCommit` until merged; never release a child on enrollment alone. For an explicitly selected GitLab repository, retain `glab mr merge <iid> --auto-merge=false --sha <source-sha> --yes`, adding `--squash` when required; follow mandatory native train protections rather than bypassing them.
7. Read the merged PR back and verify its commit reached the intended target before moving to its child. A host rejection, conflict, or advanced target requires refreshed state and a new deciding check. Do not loop on an unexplained rejection; record its concrete blocker and continue independent ready PRs.
