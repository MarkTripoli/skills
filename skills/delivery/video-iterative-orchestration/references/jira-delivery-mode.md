# Jira delivery mode

For Jira, read installed sibling `jira-issue-hierarchy/SKILL.md` and its local references for ticket authoring and Story QA readiness. When that optional skill is absent, perform read-only intake but stop before Jira issue creation or QA handoff and request its installation. No external policy fetch during run.

Jira epic = authoritative delivery queue. With no narrower selection, enumerate every eligible direct-child Story and Bug. Validate named tickets belong to the epic. A named Subtask resolves through its selected parent Story; implementation children track ownership, not QA acceptance. Bugs are direct work units, including reports from another team, and do not require invented Story parents or acceptance criteria.

Resolve eligible states from the selected Jira project workflow; the portable example is `Backlog`, `Selected for Development`, `In Progress`, and `Code Review`. Do not assume another project uses these labels. Finished-state tickets → record out of scope; never reopen, transition, correct, mutate. Same filter when delivery, correction, or design-reconciliation run resolves tickets from epic.

Always skip `On Hold` and `On-Hold`: record `skipped_on_hold`, retain existing work and findings unchanged, and do not dispatch, correct, transition or claim delivery. Refresh status before dispatch and final submission. A hold arriving during execution stops authorization at the next safe handoff, releases runtime resources and preserves published work. A newly eligible ticket re-enters normal reconciliation.

Use status to route setup. `In Progress` and `Code Review` mean implementation already exists and the Story or Bug is `resume_required`; discover and adopt its existing worktree, branch, implementation child when present, and open PR before dispatch. `Code Review` normally uses the linked PR source branch. New-delivery candidates still undergo discovery before creation.

Read + transition Jira via Jira/Atlassian MCP only. No local CLI, copied Markdown, scraped UI. Orchestrator uses MCP to: discover accessible Jira site, retrieve epic + every in-scope ticket, JQL-search epic when needed, inspect issue links + status, fetch available transitions before status change. MCP or epic access unavailable → report external blocker before dispatch. No guessed ticket content, no alternate transport.

Selected Story's requirements + acceptance criteria = sole delivery scope. Epic read only for membership, ordering, dependency context. Epic description, PRD, broad feature statement may be recorded as context; never broaden, replace, contradict, block selected ticket's work. Map only design nodes and document sections that clarify the selected Story; unmapped content creates no requirement or gap. No new requirements from epic, no selecting unlinked branches, no owner decision because epic describes different/larger feature. Preserve unrelated worktrees + branches unless linked ticket selected or prompter explicitly includes them.

Read each in-scope Story + existing Subtasks for requirements, acceptance criteria, dependencies, linked architecture docs, Figma links, existing PRs, repo context. Reuse matching agent-owned Subtask. When Story work starts, follow `jira-issue-hierarchy`'s Story-start operation: decide testability, fill the selected local Sub-task body, set the Story as Jira parent, and use `no_qa` only for non-testable work. Never create implementation children in the upfront Epic/Story breakdown; record parent key + owner in ledger. Other project → inspect issue type + fields first; use local body only if conventions fit. Never replace existing issue description with template. Never move existing issue to different parent or create second issue to match new naming rule. Map each Subtask's work to Story acceptance criteria. QA reviews Story only after `jira-issue-hierarchy`'s Story QA readiness checks pass. Submitted PRs + local evidence alone ≠ QA-ready; report pending prerequisites, never request QA review of Subtask. No architecture/Figma links → ticket requirements + acceptance criteria remain implementation + design source; absence not blocker. Jira = read-only planning context except: necessary agent-owned Subtask creation, `no_qa` on new non-testable child, Story description refresh for actual scope/evidence before QA, permitted status transitions below. Preserve existing Story criteria unless approved requirement changes; no comments, other field changes, review/done transitions, unrelated mutation unless separately authorized.

Read each Bug's observed failure, expected behavior, reproduction details, environment and acceptance criteria when present. The Bug itself remains the acceptance unit; do not require another team's spec or create a child solely to match Story topology. Missing ordinary detail uses repository behavior/tests; a material behavior conflict is an owner decision, not permission to reinterpret the report. Preserve valid existing ownership and hierarchy.

## Ticket status transitions

In-scope Story queued → MCP transition to `Selected for Development` if available + not already beyond. Right before implementation dispatch → transition Story + agent-owned Subtask (if present) to `In Progress` if available + not already there. Record actual transition in orchestration ledger.

Only transitions orchestrator performs without separate authorization. Observe Story's `Ready to test` transition only after QA readiness checks; never move agent-owned Subtask into QA state. Jira automation routes Subtasks to QA → report mismatch, don't claim Story-only handoff works. Required transition not offered → record exact available state + transition error; no substitute status, no manually driving later workflow state.

## Ticket-to-PR traceability

The orchestrator picks the smallest repository/layer scope after inspection. Each PR links its selected Story or Bug and implementation child when present, following repository title and branch conventions. A dependent PR targets its prerequisite branch and contains only its own ticket delta. New branches follow the collection's observed Git identity and ticket naming contract; existing branch names are preserved. Do not impose a company prefix, fixed worktree topology, or another repository's commit rules.

Respect Jira dependency links + epic's stated ordering when building queue. Subset prompt doesn't erase dependency: inspect it, sequence against verified branch/PR state, record genuine external dependency unsatisfiable within selected tickets.
